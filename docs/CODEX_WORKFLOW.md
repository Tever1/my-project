# Party Games Hub — Codex workflow

Этот документ описывает работу проекта без Claude. Он становится актуальным
после ручной замены корневого `AGENTS.md` текстом из
`docs/AGENTS_CODEX_ONLY_PROPOSAL.md`.

## Рабочая модель

Анастасия остаётся владельцем продукта и финальных решений. Codex выполняет
инженерную работу через специализированные чаты, а чат
`Party Games Hub — Общий прогресс` действует как системный координатор.

Разделение чатов создаёт проверяемые границы:

- общий чат хранит целостную картину проекта;
- рабочий чат держит контекст одной игры или задачи;
- отдельный review-проход проверяет рискованные изменения свежим взглядом.

## Источники истины

| Источник | Что в нём хранится | Кто синхронизирует |
|---|---|---|
| `PROJECT_CONTEXT.md` | Архитектура, product state, утверждённые правила и ограничения | Общий чат |
| `TASKS.md` | Только актуальная очередь и следующий номер отчёта | Общий чат |
| `docs/decisions/**` | Долговременные архитектурные и продуктовые решения | Общий чат после решения Анастасии |
| `codex-reports/CODEX-HANDOFF.md` | Краткая точка входа и текущее состояние | Общий чат |
| `codex-reports/NNN-*.md` | История существенных рабочих сессий и проверок | Рабочий чат |
| Git | История изменений | После явного разрешения Анастасии |

Чат помогает координации, но не заменяет канонические файлы. Старые
`.codex/STATUS.md`, `.codex/WORKFLOW.md`, `CLAUDE.md` и `codex-tasks/**` не
используются для определения текущего состояния.

## Запуск задачи

1. Анастасия открывает чат соответствующей игры или создаёт отдельный чат для
   системной задачи.
2. Codex читает `AGENTS.md`, `PROJECT_CONTEXT.md`, `TASKS.md` и релевантные ADR.
3. Codex проверяет dirty worktree и формулирует scope.
4. Если решение меняет продукт, архитектуру, privacy или правила игры, Codex
   останавливается у decision gate и получает выбор Анастасии.
5. После решения Codex реализует задачу в согласованном scope.

Для маленькой задачи отдельный task-файл не нужен. Для большой задачи план в
чате должен содержать цель, файлы/подсистемы, критерии готовности, проверки и
явные исключения.

## Завершение рабочей сессии

Рабочий чат:

1. проверяет scoped diff и отсутствие случайных файлов;
2. выполняет применимые static/runtime проверки;
3. создаёт последовательный отчёт для существенной работы;
4. сообщает точные границы проверки;
5. запускает `/context-save`.

После подтверждённой записи checkpoint `/context-save` отправляет в общий чат:

- результат сессии;
- принятые решения;
- оставшуюся работу;
- блокеры и риски;
- путь к checkpoint.

Если пересылка не сработала, рабочий чат сообщает об этом. Сохранённый
checkpoint остаётся действительным; дублирующую отправку без проверки не делать.

## Обработка сводки общим чатом

Общий чат:

1. отделяет завершённое от частично проверенного;
2. определяет влияние на другие игры и общие подсистемы;
3. обновляет `PROJECT_CONTEXT.md` только при изменении архитектуры, product
   state, утверждённого поведения или ограничений;
4. обновляет `TASKS.md`, удаляя завершённое и добавляя только актуальное;
5. синхронизирует handoff и номер следующего отчёта;
6. назначает review-проход при повышенном риске;
7. предлагает следующий приоритет, но не принимает продуктовые решения вместо
   Анастасии.

## Синхронизация roadmap A–M

Интерактивный roadmap проекта встроен во вкладку **«Этапы»** на `/admin`, а его
структурированные данные находятся в `src/lib/project-roadmap.ts`.

После завершения крупной фазы общий системный чат обязан в рамках той же
синхронизации:

1. проверить критерий завершения фазы по фактическим отчётам и проверкам;
2. обновить статус, результаты и дату в `src/lib/project-roadmap.ts`;
3. перевести следующую фазу в `active`, если нет decision gate;
4. синхронизировать краткий статус в `PROJECT_CONTEXT.md`, актуальную очередь в
   `TASKS.md` и точку входа в `codex-reports/CODEX-HANDOFF.md`;
5. не считать фазу завершённой только по визуальному макету или статической
   проверке, если её критерий требует production-интеграции либо runtime QA.

Фазы K, L и M являются обязательной частью roadmap, а не архивными идеями.

## Уровни ревью

### Локальная самопроверка

Подходит для небольшого UI/copy/type изменения с узким scope. Рабочий чат
проверяет diff, типы, lint и затронутый сценарий в разрешённых границах.

### Отдельный review-проход

Обязателен для server/realtime, TV, lobby, identity, permissions, privacy,
reconnect, shared types и крупных рефакторингов. Ревью выполняется после
реализации и до публикации, с чтением фактического diff и отчёта.

### Пользовательское утверждение

Анастасия утверждает дизайн, правила игры, приоритет, компромиссы, запуск
browser/multiplayer QA, build, commit и push.

## Параллельная работа и коллизии

- Один активный писатель на файл.
- Перед началом рабочий чат проверяет `git status` и scoped diff.
- Общие файлы (`TV`, lobby, server, shared types, канонические документы)
  считаются зонами повышенного риска пересечения.
- При пересечении scope работа останавливается до согласования порядка.
- Общий чат не редактирует production-код параллельно рабочему чату.
- Существующие unrelated изменения сохраняются без отката и форматирования.

## Нумерация

- Последовательность отчётов продолжается без привязки к наличию task-файла.
- Перед созданием отчёта сверяются `TASKS.md`, handoff и фактический максимальный
  номер в `codex-reports/`.
- При конфликте следующий номер равен максимальному фактическому номеру + 1,
  после чего канонические документы синхронизируются.
- Итерация существующей задачи может использовать `NNN.1`, если это исправление
  того же результата, а не новая самостоятельная работа.

## Публикация

По умолчанию изменения остаются локальными и незакоммиченными. Commit и push
выполняются только после явной команды Анастасии. Перед публикацией проверяются:

- список изменённых файлов;
- отсутствие защищённых или unrelated изменений в выбранном commit scope;
- результаты обязательного review;
- точность отчёта и канонического статуса;
- отсутствие одновременно работающего dev-server при production build.

PR в основную ветку готовится только после завершения scope, обязательного
review и точного перечисления выполненных и пропущенных проверок.

## Legacy

- `CLAUDE.md` сохраняется как история прежнего процесса.
- `.codex/WORKFLOW.md` и `.codex/STATUS.md` сохраняются read-only и не управляют
  текущей работой.
- `codex-tasks/**` сохраняются как архив старых ТЗ.
- `docs/AGENTS_UPDATE_PROPOSAL.md` заменён новым Codex-only предложением и не
  должен применяться вместо него.

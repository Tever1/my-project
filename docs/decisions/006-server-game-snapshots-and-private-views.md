# Server game snapshots and private views

## Context

Исторически игровой хост хранил почти всё состояние в браузере и рассылал
полный snapshot всем участникам. Это создавало три связанных риска:

- перезагрузка хоста могла остановить или сбросить активную игру;
- любой участник комнаты мог отправить действие от имени хоста или другой роли;
- приватные слова, роли, ответы и голоса попадали в чужой клиентский state.

Полный перенос семи игровых reducer-ов на backend потребовал бы переписать
production flow. Для фазы J нужен совместимый промежуточный слой, который
закрывает P1-риски без изменения утверждённых правил и дизайна.

## Decision

Socket.io server хранит в памяти канонический снимок активной игры. Каждое
`game:action` сначала проверяется по членству в комнате, текущей игре, роли и
фазе, затем применяется к серверному снимку.

Полный снимок больше не входит в `room:state`. При reconnect или
`*:request-state` сервер выдаёт адресату персонализированное представление:
скрывает чужие роли, слова, варианты ответа, голоса и другие секреты. Для
действий Mafia сервер отдельно проверяет жив ли actor, соответствует ли его
роль текущей ночной стадии и допустима ли цель. Who Am I проверяет точную
догадку по закрытому серверному снимку, а не по данным браузера игрока.

Первичный join выдаёт непрозрачный reconnect-token, который хранится локально
для пары room/player. Новый socket может занять существующий player ID только
при совпадении этого токена; публичные room snapshots токен не содержат.

Клиентские reducer-ы и существующие события сохраняются как UI-слой. Игровой
хост остаётся доверенным контроллером разрешённых host-команд, но не является
единственным источником состояния для reconnect.

## Reason

Решение совместимо с текущими production-экранами и одновременно создаёт одну
серверную точку для permissions, восстановления и фильтрации приватных данных.
Это снижает риск регрессии по сравнению с одномоментным переносом всей игровой
логики на backend.

## Alternatives

- Оставить full-state sync от браузера хоста единственным каноническим
  источником — отвергнуто из-за reconnect и privacy-рисков. Совместимые
  controller sync-патчи временно сохраняются как UI-команды, но сервер
  проверяет controller, игру и допустимый переход фазы перед их применением.
- Сразу перенести все игровые reducer-ы и таймеры на сервер — архитектурно
  чище, но слишком велико для ограниченной фазы J.
- Хранить event log или snapshots в БД — отложено до появления требований к
  persistence и горизонтальному масштабированию.

## Consequences

- Перезагрузка браузера восстанавливает активный снимок из Node-процесса;
  сервер материализует прошедшее время для активных таймеров всех семи игр,
  Quiz сохраняет закрытую очередь вопросов, Spy — рисунок, Mafia — роли и ход.
- Рестарт Node-процесса по-прежнему уничтожает комнаты и игровые снимки.
- Серверный snapshot является последним принятым состоянием, а не event log;
  production durability и multi-node deployment пока не поддерживаются.
- Новые игровые события должны получить server reducer, permission rule и
  recipient-specific privacy rule до использования в production.
- Неизвестные игровые действия отклоняются по умолчанию. Controller sync-патч
  принимается только для текущей игры и допустимого перехода фазы; «100 к 1»
  дополнительно ограничивает разрешённые поля по текущей фазе.
- Изменение требует отдельного review-прохода и multiplayer/browser regression
  перед публикацией.

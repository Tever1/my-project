## Часть 1 — Баг: счётчик «Да» подряд прыгает на 2 вместо 1

**Репро (подтверждено пользователем на 4 живых устройствах, воспроизводится
стабильно 100% времени):** во время фазы `playing`, когда активный игрок
нажимает кнопку «Да» **один раз**, бейдж «„Да" подряд: N/3» сразу показывает
`2/3` вместо ожидаемого `1/3`.

**Файл:** `src/app/game/[roomId]/who-am-i/page.tsx`

**Что я (Claude) уже проверила и исключила** (чтобы не тратить время на
повторную проверку тех же гипотез):
- Кнопка «Да» (~строка 539-545) вызывает `handleYesAnswer` (строка 281-286)
  — единственный `onClick`, дублирующего биндинга нет.
- `handleYesAnswer` вызывает `handleQuestionAsked('yes')` (строка 272-274)
  ровно один раз, без дополнительных `setGs`.
- `handleQuestionAsked` делает ровно один `broadcast({ type: 'ask-question', answer })`.
- Слушатель `game:action` зарегистрирован ровно один раз в файле (строка 146,
  `useEffect` с deps `[on]`), кейс `'ask-question'` (строка 188-210) инкрементирует
  `consecutiveYesAnswers` на `+1` через функциональный `setGs`, без второго вызова.
- `on`/`emit` берутся из единственного вызова `useSocket()` в этом компоненте
  (строка 93), никакой другой хук в `src/lib/*.ts` (`use-game-identity.ts`,
  `use-room-state.ts`) не подписывается на `game:action`.
- `socket.ts` — синглтон-соединение (`getSocket()` держит один инстанс на вкладку),
  дублирующего физического сокета для одной вкладки быть не должно.
- Сервер (`socket-handlers.mts:418-423`) делает `io.to(room).emit('game:action', ...)`
  один раз на входящее событие — стандартный паттерн, такой же как во всех
  остальных играх, там этот баг не встречается.

**Вывод:** статическим чтением кода двойной диспатч не нашла. Нужно копать
глубже — возможные направления (не ограничивайся ими, если найдёшь другую
причину):
1. Framer Motion `motion.button` (`GlassButton`, `src/components/ui/GlassButton.tsx`)
   с `whileTap` — известная категория багов: на touch-эмулируемых устройствах
   (`scripts/dev-phones.sh` открывает Chrome с touch-эмуляцией) синтетический
   клик после `pointerup`/`touchend` иногда дублируется с нативным `click`.
   Проверь, не проявляется ли двойной `onClick` именно на touch-устройствах.
2. HMR/Fast Refresh в dev-режиме (Turbopack) может оставлять «осиротевший»
   листенер на модульном singleton-сокете, если cleanup эффекта не отработал
   корректно при быстрой перезагрузке модуля — проверить, воспроизводится ли
   баг в production build (`npm run build && npm run start`), а не только в dev.
3. Добавь временный `console.log` в кейс `'ask-question'` (кол-во вызовов +
   `payload`) и в `handleYesAnswer`, воспроизведи баг локально (можно через
   `npm run phones -- <CODE> 4`), убедись сколько раз реально срабатывает
   кейс на один клик — это даст точный ответ вместо гипотез. Убери логи
   после диагностики.

**Требование:** один клик «Да» → счётчик увеличивается ровно на 1, ровно один
раз обновляется `questionsAsked` для текущего игрока. Поведение «Нет» —
аналогично проверить (по логике та же схема, баг может быть общим для обоих
путей, просто на «Нет» это незаметно, т.к. счётчик серии не отображается).

## Часть 2 — Механика «оспорить ответ» для угадывания персонажа

**Контекст:** в игре «Шпион» (`src/app/game/[roomId]/spy/page.tsx`, ~строки
1196-1263) уже есть похожая механика для угадывания слова шпионом — используй
её как образец паттерна (НЕ трогай файл spy, только читай для референса):
- Игрок вводит текст, жмёт «Проверить» → `spy:guess-try`.
- Если автоматическое сравнение (`normalise()`) не совпало — показывается
  «Не совпало автоматически. Настаиваешь, что верно?» с кнопкой «Подтвердить»
  (`spy:guess-confirm`).
- После подтверждения кто-то из ОСТАЛЬНЫХ игроков становится «судьёй»
  (`isJudge && s.spyGuessAwaitingJudge`) и видит две карточки — что ввёл
  игрок vs правильное слово, с кнопками «Верно» / «Отклонить»
  (`spy:guess-verdict`, `{ accept: true/false }`).
- Состояние: `spyGuessNeedsConfirm`, `spyGuessAwaitingJudge`, `spyGuessText`.

**Задача:** реализовать аналогичный флоу для угадывания персонажа в
«Кто я?» (`handleGuess`, строка 291-307 в `who-am-i/page.tsx`). Сейчас
сравнение строгое (`normalise(guessInput) === normalise(myChar.ru/en)`) —
опечатка = засчитывается как неправильный ответ без права оспорить.

Нужно:
1. Если `normalise()` не совпало — вместо немедленного `broadcast({type:'guess', correct:false, ...})`
   показать игроку экран «Не совпало автоматически. Настаиваешь, что верно?»
   с кнопкой «Подтвердить» (по аналогии со Spy).
2. При подтверждении — выбрать судью среди ОСТАЛЬНЫХ игроков (не сам угадывающий,
   не тот, чей это персонаж — подумай, кто логично: вероятно, любой другой игрок
   в комнате, кроме самого угадывающего). Судья видит: что ввёл игрок vs
   правильное имя персонажа, кнопки «Верно» / «Отклонить».
3. Вердикт судьи определяет `correct` в итоговом `broadcast({ type: 'guess', ... })`
   — переиспользуй существующий кейс `'guess'` в редьюсере (строка 212-242),
   он уже обрабатывает `correct: true/false` корректно (начисление очков,
   переход хода). Просто финальное значение `correct` теперь берётся из
   вердикта судьи, а не только из строгого сравнения.
4. Расширь `WhoAmIGameState`/`GameAction` типы как это сделано у Spy (доп.
   поля вроде `guessNeedsConfirm`, `guessAwaitingJudge`, `guessJudgeId`,
   `guessPendingText` — придумай точные имена по аналогии, главное —
   консистентность с уже существующим стилем файла).
5. **TV-зеркало** (`src/app/tv/[roomId]/[gameType]/page.tsx`, блок
   `gameType === 'who-am-i'`, интерфейс `WhoAmIState`/`WhoAmIAction` ~строка
   135-160): синхронизируй тип состояния с новыми полями (TV слушает
   пассивно через `sync-state`/точечные экшены — TV НЕ должен получить
   собственный UI судьи, это чисто мобильный флоу; но TV не должен падать
   с TS-ошибкой из-за расхождения типов, и желательно показать что-то
   нейтральное типа «Игрок оспаривает ответ…», если легко добавить —
   не обязательно, если усложняет).

**Двуязычность:** все новые строки — через существующий хелпер `l(ru, en)`
в файле, обе локали обязательны (правило проекта, см. CLAUDE.md п.1).

# TASK-508: аудит переходов «100 к 1»

## Результат

По запросу Анастасии проверены кнопки смены этапов: выбор темы, Далее после
ролей, подтверждения капитанов и названий, Пропустить, Начать игру, buzzer,
следующие раунды, правила раунда 4, Итоги, Большая игра, оба этапа проверки,
финал, повтор и выход в лобби. Production-код в этой проверке не изменялся.
Предыдущее исправление TASK-507 остаётся локальным и требует restart backend.

## Подтверждённые находки

1. **P1 — title → buzzer: «Начать игру» у хоста комнаты.** UI разрешает
   `isHost || isGameHost`, сервер — только роль `host` H2O. Если ведущий другой
   человек, команда комнатного хоста отклоняется, но его локальный экран
   оптимистически меняется. Аналог TASK-507 на следующем этапе.
2. **P1 — почти одновременные подтверждения капитанов.** Каждая команда
   передаёт обе команды в captains/captainConfirmed. Пакет второй команды,
   сформированный до получения первого подтверждения, отклоняется сервером
   из-за устаревшего состояния чужой команды. Сервер остаётся в captainSelect.
   Локальное подтверждение на отправителе уже скрывает кнопку, пока состояние
   не будет восстановлено серверным snapshot.
3. **P1 — почти одновременные подтверждения названий.** Та же проблема с
   teamNameConfirmed: второй капитан передаёт устаревший чужой флаг, сервер
   отклоняет команду и остаётся в teamNames.
4. **P1 — «Пропустить» выбор капитанов создаёт тупик.** Ведущий может перейти
   к teamNames без капитанов. Поле и кнопка названия доступны только капитану;
   капитанов нет, у ведущего только ожидание. Подтверждение от участника без
   статуса капитана сервер отклоняет. Это не отказ перехода: сам переход
   проходит, но следующее состояние нельзя завершить обычными кнопками.

Источники: `src/app/game/[roomId]/hundred-to-one/page.tsx` — confirmCaptain,
confirmMyTeamName, title/captainSelect/teamNames render; серверная функция
isAuthorizedH2OSync в `src/server/socket-handlers.mts`.

## Проверки и границы

- Добавлен `src/server/h2o-transitions.audit.test.mts`: воспроизводит все четыре
  находки через реальные Socket.io handlers на отдельном временном сервере,
  4 игрока + TV; room host играет в команде, ведущий — отдельный игрок.
- Это characterization-тест: зелёный результат подтверждает наличие
  описанных дефектов, а не их исправление. При исправлении изменить ожидания.
- Задержка обновлений проверяется детерминированно: второй пакет сформирован
  из того же исходного snapshot, что и первый, как при одновременных нажатиях.
- Существующие H2O-тесты проходят: TASK-507 regression и 58 protocol checkpoints
  от setup до replay. Поздние переходы соответствуют правам ведущего;
  разрешения game:end включают комнатного хоста и ведущего H2O.
- TypeScript, scoped ESLint и git diff --check проходят.
- Browser/manual QA, production build, restart, commit и push не выполнялись.
- Общие управляющие документы не редактировались. Фактический следующий номер
  после отчёта — 509; синхронизация нумерации остаётся за общим чатом.

## Рекомендованное продолжение

Согласовать видимость «Начать игру» с серверным разрешением. Подтверждения
капитанов/названий применять на сервере только к собственной команде отправителя,
вычисляя завершение общего этапа по каноническому snapshot. Отдельно определить
смысл «Пропустить»: переход не должен оставлять команды без доступного действия.
Исправление найденных проблем в этот запрос проверки не включалось.
